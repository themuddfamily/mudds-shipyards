## Implementation strategy — playable core first

The phase and feature lists below remain the complete intended scope. This strategy changes **execution order and acceptance discipline**, not the destination. Work proceeds in small vertical increments: stabilize the current packaged game, add one bounded feature slice, restore every stability gate, then produce the next checkpoint build. A later phase may be researched or prototyped in isolation, but it does not displace unresolved core-loop defects.

### Priority order

1. **P0 — cannot continue safely:** editor/import failure, crash, corrupted save/configuration, invalid package, unrecoverable soft-lock, authority duplication, or a regression that can destroy or permanently strand gameplay state. Stop other implementation until reproduced, fixed, and package-verified.
2. **P1 — core loop blocked or misleading:** cannot reach a required route without an unintended jump, visible walkable surface lacks collision, interaction/boarding cannot be acquired from its intended approach, character or craft presentation contradicts authoritative movement, landing cannot be acquired reasonably, required prompts are absent, or a texture/material defect systematically reverses or destroys scene readability. P1 work takes precedence over new art, rooms, ships, weapons, or activities.
3. **P2 — playable but materially rough:** camera discomfort, poor control tuning, unclear feedback, local clipping, isolated visual mismatch, weak mix, avoidable friction, or recoverable lifecycle inconsistency. Batch these into short polish passes between P1 closure and the next content slice.
4. **P3 — expansion and optional polish:** new modules, ships, combat breadth, multiplayer, destinations, decorative density, and speculative fidelity improvements. These remain planned below and resume only while the active prototype gate is green.

Bug status is independent from severity: `CANDIDATE` → `NEW` → `REPRODUCED` → `FIXING` → `VERIFYING` → `CLOSED`. Use `NOT_REPRODUCED` when the recorded scenario produces zero failures in ten attempts across two documented configurations; use `ACCEPTED_RISK` only with rationale and owner. Never mark an unreproduced report closed. Every intake record includes stable ID/title, reporter/date, first/last affected source and artifact hashes, OS/CPU/GPU/RAM/driver/audio/input/resolution/profile, clean or retained user-data state, numbered steps, expected/actual result, failure frequency, affected loop beat, log/image/video paths and hashes, severity, owner, linked reproducer/regression, and disposition.

### Required work-item contract

Every implementation item—bug fix or feature—must record the following before it can be called complete:

- **Player-visible outcome:** one sentence describing what the player can now do or perceive.
- **Authority owner:** the exact node/resource responsible for state. Presentation may observe authority but must not silently duplicate collision, damage, leases, movement, scoring, interaction, or regeneration.
- **Implementation seam:** the smallest existing component/API to change; new parallel systems require an explicit reason.
- **Reproduction or scenario:** deterministic starting state, input sequence, expected result, and failure witness. A bug begins with a failing witness; a feature begins with an acceptance scenario.
- **Focused regression:** a permanent test against the production scene/component, including at least one structured-red mutation or boundary case when the feature has authority or lifecycle risk.
- **Integration regression:** the complete affected player path through real `Main`, not only an isolated fixture.
- **Package parity:** the source fix is not accepted for a downloadable prototype until the exported Windows pack reproduces the corrected behaviour or passes an equivalent external probe.
- **Presentation and device checks:** verify controls, visual readability, texture direction and comfort through automated scenarios and rendered inspection; retain real-device audio audibility checks. Headless assertions do not establish audible output or target-GPU performance.

### Design and implementation specification
