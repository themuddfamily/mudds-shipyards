## Implementation strategy — playable core first

The phase and feature lists below remain the complete intended scope. This strategy changes **execution order and acceptance discipline**, not the destination. Work proceeds in small vertical increments: stabilize the current packaged game, add one bounded feature slice, restore every stability gate, then produce the next playtest build. A later phase may be researched or prototyped in isolation, but it does not displace unresolved core-loop defects.

### Priority order

1. **P0 — cannot continue safely:** editor/import failure, crash, corrupted save/configuration, invalid package, unrecoverable soft-lock, authority duplication, or a regression that can destroy or permanently strand gameplay state. Stop other implementation until reproduced, fixed, and package-verified.
2. **P1 — core loop blocked or misleading:** cannot reach a required route without an unintended jump, visible walkable surface lacks collision, interaction/boarding cannot be acquired from its intended approach, character or craft presentation contradicts authoritative movement, landing cannot be acquired reasonably, required prompts are absent, or a texture/material defect systematically reverses or destroys scene readability. P1 work takes precedence over new art, rooms, ships, weapons, or activities.
3. **P2 — playable but materially rough:** camera discomfort, poor control tuning, unclear feedback, local clipping, isolated visual mismatch, weak mix, avoidable friction, or recoverable lifecycle inconsistency. Batch these into short polish passes between P1 closure and the next content slice.
4. **P3 — expansion and optional polish:** new modules, ships, combat breadth, multiplayer, destinations, decorative density, and speculative fidelity improvements. These remain planned below and resume only while the active prototype gate is green.

Bug status is independent from severity: `CANDIDATE` → `NEW` → `REPRODUCED` → `FIXING` → `VERIFYING` → `CLOSED`. Use `NOT_REPRODUCED` when the recorded scenario produces zero failures in ten attempts across two documented configurations; use `ACCEPTED_RISK` only with rationale and owner. Never mark an unreproduced report closed. Every intake record includes stable ID/title, reporter/date, first/last affected source and artifact hashes, OS/CPU/GPU/RAM/driver/audio/input/resolution/profile, clean or retained user-data state, numbered steps, expected/actual result, failure frequency, affected loop beat, log/image/video paths and hashes, severity, owner, linked reproducer/regression, and disposition.

### Stabilization stages

1. **Gate A — reproducible baseline:** add a checked-in one-command runner that recursively discovers `tests/**/*_test.gd`, freezes the sorted roster, gives each suite a timeout, requires exit `0` and exactly one accepted terminal sentinel, counts anchored assertions, scans raw logs for failure/error/leak/orphan diagnostics, hashes every log/result file, and proves the runnable-source manifest is unchanged before/after. Use the runner-discovered sorted roster rather than a hard-coded suite total. Historical matrices remain in the dated archive; Gate A requires a new source-pinned record.
2. **Gate B — stabilization closure:** reproduce or explicitly disposition every active P0/P1 and current review candidate. Each closed defect needs a before-failing/after-green regression, focused and full matrix, current-package scenario rerun, and independent verification for P0/P1.
3. **Gate C — packaged core scenarios:** run three scripts without debug shortcuts. **Guided:** cold boot → begin → walk/board Torrent → apply thrust for same-tick automatic power → physical launch → targets/defender → lease landing → `1.5` physics seconds of neutral automatic shutdown → disembark → completion. **Sandbox:** traverse Central/Aft/Habitat/Freight/Fleet Dock; launch/land/exit Arrow, Jovian, Zenith, Halyard, Bulwark and all three Cinder craft; deliberately crash; recover on foot; regenerate and reuse a craft. **Settings/re-entry:** save settings → restart → pause/resume → camera modes → all required keyboard/mouse and current gamepad lifecycle controls. Require Guided 3/3 consecutive fresh-process passes, Sandbox 1/1, Settings 1/1.
4. **Gate D — external tuning:** five first-time Windows players may use in-game help but receive no developer intervention. At least four must launch, fight, redock, and disembark within 30 minutes; median camera comfort, control clarity, and landing clarity must each be at least 4/5; any P0/P1 returns the project to Gate B.
5. **Gate E — candidate/performance:** export from one exact clean commit with a unique build label. 6. **Gate F — controlled expansion resume:** all nine current craft/package scenarios, frozen matrix, external thresholds, performance candidate, zero P0/P1, and no accepted core-loop P2. Resume the existing Phase 1–9 backlog with a WIP limit of one authority-bearing runtime slice. Pause expansion again on any P0/P1, editor/import or full-matrix failure, two open core-loop P2s in one subsystem, Guided below 3/3, external completion below 4/5, same-hardware p95 regression above 10%, or mismatched source/artifact evidence. Fixes may cut an immediate candidate, but otherwise produce at most one internal candidate after a clean day and one public preview only after two consecutive candidate gates; permission/legal/licensing and signing requirements still apply.

### Required work-item contract

Every implementation item—bug fix or feature—must record the following before it can be called complete:

- **Player-visible outcome:** one sentence describing what the player can now do or perceive.
- **Authority owner:** the exact node/resource responsible for state. Presentation may observe authority but must not silently duplicate collision, damage, leases, movement, scoring, interaction, or regeneration.
- **Implementation seam:** the smallest existing component/API to change; new parallel systems require an explicit reason.
- **Reproduction or scenario:** deterministic starting state, input sequence, expected result, and failure witness. A bug begins with a failing witness; a feature begins with an acceptance scenario.
- **Focused regression:** a permanent test against the production scene/component, including at least one structured-red mutation or boundary case when the feature has authority or lifecycle risk.
- **Integration regression:** the complete affected player path through real `Main`, not only an isolated fixture.
- **Package parity:** the source fix is not accepted for a downloadable prototype until the exported Windows pack reproduces the corrected behaviour or passes an equivalent external probe.
- **Human check:** controls, visual readability, texture direction, audio audibility, and comfort require real-time review; headless assertions do not substitute for perception.

Unconfirmed audit observations stay in [`bugs.md`](bugs.md) until reproduced. Confirmed P0/P1 defects move into the active Phase 2 stabilization checkpoint with a failing witness and owner; resolved items remain recorded with their regression gate instead of being silently deleted.

### Content-slice cadence

After the gate above is green, each feature slice follows this order: **specification → isolated implementation → focused tests → production integration → physical player-path test → rendered/audio review → full matrix → packaged smoke → human playtest**. Only one authority-bearing slice should be in integration at a time. Presentation-only asset work may run in parallel when it touches disjoint files and consumes already frozen semantic anchors. Any new P0/P1 re-enters stabilization immediately; the unfinished feature stays paused rather than being layered over a broken baseline.

### Junior developer delivery checklist

Use this sequence for every roadmap task. Do not skip directly from an isolated scene looking correct to editing `Main`.

1. Read the relevant phase specification, existing component script, scene, focused test, integration test, `RESEARCH.md`/evidence spec when historically labelled, and `ASSETS.md` when adding art/audio/material bytes.
2. Write the player-visible outcome and list the files you expect to touch. Identify the current authority owner and signal/API boundary. If ownership is unclear, stop and document it before coding.
3. Run the editor/import gate and the existing focused test once to establish a clean baseline. For a bug, add or run a deterministic failing reproduction before changing production code.
4. Implement the smallest change behind the existing public API. Avoid direct node-path access from unrelated systems when a typed getter/signal/component already exists.
5. Extend the component audit with stable IDs, exact rosters/budgets, authority flags, and structured errors. Return deep copies of mutable reports so callers cannot mutate component state.
6. Add focused tests for the normal case, exact boundary, invalid input, duplicate/re-entry/reset behaviour, and at least one mutation that must turn the audit red. Do not assert only node existence.
7. Add a production integration test through `res://scenes/main.tscn`. Drive normal inputs/components and verify the player-visible result plus unchanged adjacent authority.
8. If geometry or mapping changed, run native Forward+ at the shipping resolution/profile and inspect original-resolution frames. If audio changed, audition on real output hardware at multiple mix levels/distances.
9. Run affected neighbouring suites, then the complete isolated-process matrix. Treat new warnings, leaks, timeouts, orphan/RID diagnostics, or altered source bytes during validation as failures until explained.
10. Export from the exact tested commit, inspect the PE/PCK metadata, smoke the embedded pack from a clean directory, run external package probes where available, and complete the human scenario. Record artifact hash and outstanding limitations.

The minimum change report should state: outcome, root cause/design decision, files, tests/assertions, native/human evidence, package hash, and remaining risks. A junior developer should be able to hand that report to a reviewer without relying on unstated conversation context.

## Phase 2 — Vertical slice

### Design and implementation specification

- `GameFlow` coordinates the solo loop and UI phase; it must not become the physics owner of the Player, a ship, a berth, a weapon hit, or a station door. `PlayerController` owns embodied movement, `HeroShip`/ship subclasses own craft simulation, `ShipBerth` owns lease/occupancy, `ShipBoardingArea` owns access/reservation, `CombatResolver` owns accepted hit results, and presentation components consume signals without changing those results.
- Keep the playable route physical. Core acceptance uses the production `CharacterBody3D`, real collision layers, real `InputMap` actions, real boarding areas, real seat anchors, real ship commands, and real berth leases. Teleports and direct state changes may set up a test but cannot be the evidence that the route itself works.
- Keep visible and physical geometry intentionally paired. A collision-only ramp may smooth movement only when a rendered surface occupies the same plane within the player-foot tolerance; decorative tread, inset, trim, grille, or shell meshes must be explicitly tagged non-walkable. Discover broad upward-facing route meshes in addition to maintaining a curated critical-surface roster.
- Keep movement authority and model orientation separate. Camera-relative input determines desired velocity; `CharacterBody3D` moves in that direction; the active visual mount applies only the model-specific forward-axis correction. Never fix a backwards-facing model by reversing input, velocity, camera axes, or animation semantics.
- Split material families by use. Authored ship atlases remain on their registered craft; procedural station architecture uses station-specific, lighting-neutral, tileable PBR maps with module/world-stable projection; authored hero surfaces use metric UV0. Tests must pin texture identity, importer normal convention, handedness, edge continuity, texel density, and the live material bindings rather than only checking that a texture exists.
- Landing assist is acquisition and guidance, not authority bypass. A broad capture volume may brake, stage, and align a compatible ship at forgiving speed/attitude limits; the final dock still requires the strict hull envelope, unobstructed path, valid requester-bound lease, exact berth identity, and occupy-before-snap ordering.
- Boarding reach must be wide enough for collision-clear approaches and must select the nearest eligible ship deterministically. It may not enlarge station-door reach, cross an opposite hull, ignore a disabled/reserved `ShipBoardingArea`, or clear the post-exit reboard latch before leaving the full boarding envelope.
- Combat chronology is authority first, presentation at travel arrival: health/collision/scoring resolve once; pulse receipt completion releases impact/explosion/audio once; abort/recycle releases any deferred record atomically. Pools and re-entry cleanup are bounded and cannot allocate gameplay authority.
- Vertical-slice exit gate: the complete playable-prototype gate above, plus human tuning of on-foot camera, flight, landing, boarding, combat readability, audibility, and recovery in the same packaged candidate.

## Phase 3 — Shipyard expansion (bounded operational-lattice slice settled; full phase incomplete)

### Design and implementation specification

- Build each station addition as a bounded module scene with a stable module ID, identity connection anchor, local footprint/AABB, route-marker registry, evidence metadata, semantic component roster, collision/authority/performance report, validation API, and reversible enable/disable lifecycle. World integration owns the global transform and any shared gameplay authority.
- Preserve a single station graph. A module publishes connection planes and route endpoints; `ShipyardWorld` chooses placement and proves adjacency. Do not hide disconnected geometry with teleport triggers, duplicate floors, invisible bridges, or presentation-only shells that imply a route the player cannot walk.
- Separate walkable structure from dressing. Walkable decks, ramps, stairs, shelves, and thresholds use World-layer static collision matched to their visible envelope. Pipes, labels, rails, lamps, trim, machinery covers, and distant shells are collision-free unless they intentionally block the player, and non-walkable horizontal presentation is tagged for discovery audits.
- Keep berth, regeneration, door, activity, and audio ownership external or explicit. A decorative dock marker cannot reserve a ship; a labelled control cannot regenerate one; an activity rail cannot become navigation; an ambience emitter cannot drive a door. New modules consume the existing component APIs instead of creating lookalike local authority.
- Integrate in dependency order: evidence/topology claim → isolated module scene → module audit/test → collision-clear connection transform → production-world route test → nearby berth/ship-envelope regression → Main detach/re-entry → native overview and player-height review.
- Expansion acceptance requires: no changed existing berth transforms/leases unless explicitly scoped; continuous no-jump route from an existing hub; published negative-space samples remain empty; visible floor support discovery stays green; no overlap with landing capture/final hull envelopes; quality-profile budgets are bounded; full core-loop/package gates remain green.
