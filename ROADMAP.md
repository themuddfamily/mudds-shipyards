# Development roadmap

This roadmap preserves the full remake objective while keeping implementation ordered around a polished physical core. The current state is an **early Phase 2 prototype with a settled, bounded Phase 3 operational-lattice slice and bounded Phase 4 foundations**, with Phase 1 authenticity research continuing in parallel. The active delivery strategy is **playable core first**: feature scope remains in this roadmap, but new content waits behind explicit stability gates for the existing walk/board/fly/fight/land/disembark loop. A checked item means that bounded implementation or research milestone exists; it does not declare the phase, the overall objective, or an authentic historical reconstruction complete.

The visual target is a realistic-looking, polished stylised high-end PC presentation—not literal photorealism—that preserves Keth's clean silhouettes, readable colours, and playful scale. Much of the station and remaining fleet is still procedural prototype work, while the bounded Torrent, bounded B7-observed Blender-authored Zenith, skinned pilot and Blender-authored central-berth shell establish the imported-art pipeline. None is final production art or an authenticated historical reconstruction.

## Implementation strategy — playable core first

The phase and feature lists below remain the complete intended scope. This strategy changes **execution order and acceptance discipline**, not the destination. Work proceeds in small vertical increments: stabilize the current packaged game, add one bounded feature slice, restore every stability gate, then produce the next playtest build. A later phase may be researched or prototyped in isolation, but it does not displace unresolved core-loop defects.

### Priority order

1. **P0 — cannot continue safely:** editor/import failure, crash, corrupted save/configuration, invalid package, unrecoverable soft-lock, authority duplication, or a regression that can destroy or permanently strand gameplay state. Stop other implementation until reproduced, fixed, and package-verified.
2. **P1 — core loop blocked or misleading:** cannot reach a required route without an unintended jump, visible walkable surface lacks collision, interaction/boarding cannot be acquired from its intended approach, character or craft presentation contradicts authoritative movement, landing cannot be acquired reasonably, required prompts are absent, or a texture/material defect systematically reverses or destroys scene readability. P1 work takes precedence over new art, rooms, ships, weapons, or activities.
3. **P2 — playable but materially rough:** camera discomfort, poor control tuning, unclear feedback, local clipping, isolated visual mismatch, weak mix, avoidable friction, or recoverable lifecycle inconsistency. Batch these into short polish passes between P1 closure and the next content slice.
4. **P3 — expansion and optional polish:** new modules, ships, combat breadth, multiplayer, destinations, decorative density, and speculative fidelity improvements. These remain planned below and resume only while the active prototype gate is green.

Bug status is independent from severity: `CANDIDATE` → `NEW` → `REPRODUCED` → `FIXING` → `VERIFYING` → `CLOSED`. Use `NOT_REPRODUCED` when the recorded scenario produces zero failures in ten attempts across two documented configurations; use `ACCEPTED_RISK` only with rationale and owner. Never mark an unreproduced report closed. Every intake record includes stable ID/title, reporter/date, first/last affected source and artifact hashes, OS/CPU/GPU/RAM/driver/audio/input/resolution/profile, clean or retained user-data state, numbered steps, expected/actual result, failure frequency, affected loop beat, log/image/video paths and hashes, severity, owner, linked reproducer/regression, and disposition.

### Stabilization stages

1. **Gate A — reproducible baseline:** add a checked-in one-command runner that discovers `tests/*_test.gd`, freezes the sorted roster, gives each suite a timeout, requires exit `0` and exactly one accepted terminal sentinel, counts anchored assertions, scans raw logs for failure/error/leak/orphan diagnostics, hashes every log/result file, and proves the runnable-source manifest is unchanged before/after. The present 77-suite/7,070-assertion pass is useful working-tree evidence, but the recorded 75-suite matrix remains the latest frozen checkpoint until this runner produces a source-pinned record.
2. **Gate B — stabilization closure:** reproduce or explicitly disposition every active P0/P1 and current review candidate. Each closed defect needs a before-failing/after-green regression, focused and full matrix, current-package scenario rerun, and independent verification for P0/P1.
3. **Gate C — packaged core scenarios:** run three scripts without debug shortcuts. **Guided:** cold boot → begin → walk/board Torrent → start → physical launch → targets/defender → lease landing → shutdown → disembark → completion. **Sandbox:** traverse Central/Aft/Habitat/Freight/Fleet Dock; launch/land/exit Arrow, Jovian, Zenith; deliberately crash; recover on foot; regenerate and reuse a craft. **Settings/re-entry:** save settings → restart → pause/resume → camera modes → all required keyboard/mouse and current gamepad lifecycle controls. Require Guided 3/3 consecutive fresh-process passes, Sandbox 1/1, Settings 1/1.
4. **Gate D — external tuning:** five first-time Windows players may use in-game help but receive no developer intervention. At least four must launch, fight, redock, and disembark within 30 minutes; median camera comfort, control clarity, and landing clarity must each be at least 4/5; any P0/P1 returns the project to Gate B.
5. **Gate E — candidate/performance:** export from one exact clean commit with a unique build label. Record source commit, matrix record, Godot version, EXE size/hash, PE version, embedded PCK inventory, signing state, smoke result, and hardware. Initial proposed 1920×1080 High benchmark after 60 seconds warm-up: ten-minute representative route, p95 ≤16.7 ms, p99 ≤33.3 ms, no post-warm-up frame >100 ms, peak working set ≤4 GiB. Record CPU/GPU/RAM/driver/audio device; these are design budgets until representative hardware validates them.
6. **Gate F — controlled expansion resume:** four current craft/package scenarios, frozen matrix, external thresholds, performance candidate, zero P0/P1, and no accepted core-loop P2. Resume the existing Phase 1–9 backlog with a WIP limit of one authority-bearing runtime slice. Every merged runtime slice invalidates relevant package/human evidence and returns through the affected gates before the next slice.

Pause expansion again on any P0/P1, editor/import or full-matrix failure, two open core-loop P2s in one subsystem, Guided below 3/3, external completion below 4/5, same-hardware p95 regression above 10%, or mismatched source/artifact evidence. Fixes may cut an immediate candidate, but otherwise produce at most one internal candidate after a clean day and one public preview only after two consecutive candidate gates; permission/legal/licensing and signing requirements still apply.

### Required work-item contract

Every implementation item—bug fix or feature—must record the following before it can be called complete:

- **Player-visible outcome:** one sentence describing what the player can now do or perceive.
- **Authority owner:** the exact node/resource responsible for state. Presentation may observe authority but must not silently duplicate collision, damage, leases, movement, scoring, interaction, or regeneration.
- **Implementation seam:** the smallest existing component/API to change; new parallel systems require an explicit reason.
- **Reproduction or scenario:** deterministic starting state, input sequence, expected result, and failure witness. A bug begins with a failing witness; a feature begins with an acceptance scenario.
- **Focused regression:** a permanent test against the production scene/component, including at least one structured-red mutation or boundary case when the feature has authority or lifecycle risk.
- **Integration regression:** the complete affected player path through real `Main`, not only an isolated fixture.
- **Package parity:** the source fix is not accepted for a downloadable prototype until the exported Windows pack reproduces the corrected behaviour or passes an equivalent external probe.
- **Human check:** controls, visual readability, texture direction, audio audibility, and comfort require real-time review; headless assertions do not substitute for perception.

Unconfirmed audit observations stay in [`bugs.md`](bugs.md) until reproduced. Confirmed P0/P1 defects move into the active Phase 2 stabilization checkpoint with a failing witness and owner; resolved items remain recorded with their regression gate instead of being silently deleted.

### Playable-prototype gate

The next expansion slice may begin only when one fresh, source-pinned Windows candidate satisfies all of these conditions:

- Boots into the title and starts a shift without `ERROR`, `SCRIPT ERROR`, `FATAL`, rejection, orphan, resource-leak, or invalid-authority diagnostics.
- The on-foot avatar visibly faces its actual horizontal velocity for forward, back, strafe, and diagonal movement at multiple camera headings; input/velocity must not be reversed to compensate for art orientation.
- A no-cheat traversal from spawn reaches the Central berth, Aft upper level, Habitat, Freight branch, and Fleet Dock walking surfaces without falling through, snagging on decorative treads, or requiring an undocumented jump. Every broad route surface that visually reads as floor/deck/ramp must have immediate World collision support or explicit non-walkable presentation metadata.
- Station floor/wall/stair materials use a coherent station material family with continuous metric mapping; ship-specific atlases stay on their registered ships. Authored UV0 surfaces have non-degenerate, consistent outward-view handedness and bounded texel-density distortion.
- All four ships can be approached from collision-clear routes, boarded through the production reservation path, started, launched, flown, fired, returned with forgiving assist acquisition, strictly docked, shut down, and exited. Destroy/recover/switch-craft reuse must not duplicate authority or strand a berth.
- The guided Torrent loop completes only after its actual combat, return, dock, shutdown, and disembark lifecycle, once per generation.
- The complete sorted `tests/*_test.gd` matrix passes in isolated processes after a clean editor/import gate, with exact terminal sentinels and no unreviewed diagnostics.
- A human completes at least one uninterrupted packaged sortie using normal controls—no harness teleport, direct state mutation, or debugger shortcut—and records control, camera, collision, texture, prompt, audio, and performance observations.

### Content-slice cadence

After the gate above is green, each feature slice follows this order: **specification → isolated implementation → focused tests → production integration → physical player-path test → rendered/audio review → full matrix → packaged smoke → human playtest**. Only one authority-bearing slice should be in integration at a time. Presentation-only asset work may run in parallel when it touches disjoint files and consumes already frozen semantic anchors. Any new P0/P1 re-enters stabilization immediately; the unfinished feature stays paused rather than being layered over a broken baseline.

### Junior developer delivery checklist

Use this sequence for every roadmap task. Do not skip directly from an isolated scene looking correct to editing `Main`.

1. Read the relevant phase specification, existing component script, scene, focused test, integration test, `RESEARCH.md`/evidence spec when historically labelled, and `ASSETS.md` when adding art/audio/material bytes.
2. Write the player-visible outcome and list the files you expect to touch. Identify the current authority owner and signal/API boundary. If ownership is unclear, stop and document it before coding.
3. Run the editor/import gate and the existing focused test once to establish a clean baseline. For a bug, add or run a deterministic failing reproduction before changing production code.
4. Implement the smallest change behind the existing public API. Avoid direct node-path access from unrelated systems when a typed getter/signal/component already exists.
5. Extend the component audit with stable IDs, exact rosters/budgets, authority flags, and structured errors. Return deep copies of mutable reports so callers cannot mutate component state.
6. Add focused tests for the normal case, exact boundary, invalid input, duplicate/re-entry/reset behaviour, and at least one mutation that must turn the audit red. Do not assert only node existence.
7. Add a production integration test through `res://scenes/main.tscn`. Drive normal inputs/components and verify the player-visible result plus unchanged adjacent authority.
8. If geometry or mapping changed, run native Forward+ at the shipping resolution/profile and inspect original-resolution frames. If audio changed, audition on real output hardware at multiple mix levels/distances.
9. Run affected neighbouring suites, then the complete isolated-process matrix. Treat new warnings, leaks, timeouts, orphan/RID diagnostics, or altered source bytes during validation as failures until explained.
10. Export from the exact tested commit, inspect the PE/PCK metadata, smoke the embedded pack from a clean directory, run external package probes where available, and complete the human scenario. Record artifact hash and outstanding limitations.

The minimum change report should state: outcome, root cause/design decision, files, tests/assertions, native/human evidence, package hash, and remaining risks. A junior developer should be able to hand that report to a reviewer without relying on unstated conversation context.

## Art direction — player feedback, 2026-08-15

After playtesting the traversal fixes the player confirmed the layout is right — *"I wanted the same map and everything, yes we have that, perfect"* — and gave a specific direction for the presentation: it currently **looks too close to the original Keth's Shipyards**, and should **feel more realistic than Keth's did**, i.e. **"more like its own game, less like Roblox."**

This does not change the stated visual target above; it records that the target has not been reached, and sharpens what "reached" means:

- **Layout, adjacency, silhouettes and scale are correct and must not be changed** to chase realism. The evidence boundary and the recovered/inferred station shape stay exactly as they are.
- What must change is **how surfaces read**. The current presentation reads as untextured primitives: flat scalar colour over large areas, sharp unbevelled 90° edges, uniform roughness, and little contact shading. Those four properties, not the shapes, are what make blocky geometry read as a toy.
- Highest-leverage work, in rough order: edge bevelling/chamfering on structural geometry so edges catch a highlight; extending the station material family to the wider lattice, catwalks and control room, which are still entirely flat scalar; ambient-occlusion and indirect-light tuning at the station's actual 10–50 m scale rather than defaults; tonemapping and specular response; and lighting coherence.
- Two parts of this remain **outside what can be produced headlessly** and need a human artist: final authored/baked/scanned normal/roughness/ORM sets, and the curved/bevelled *authored* geometry pass on ships. Procedural bevelling of structural primitives and material-family extension are achievable here; authored art is not.

Presentation changes require real-time human review; automated checks cannot establish that something reads as a manufactured place.

### Station lighting pass — 2026-08-16

Three independent surface passes (post-processing, ship detail, chamfering) each reported the same ceiling in different words: the material and geometry work was landing on surfaces too dark to show it. Measured mean frame luminance before this pass ran 2–27 out of 255 across parked berths, the engine cluster, the operations room and the gantry, and the *median* pixel of every one of those frames sat at 14–17/255. Screen-space AO modulates ambient and there was almost no ambient to modulate; `normal_scale` at an absurd 12.0 moved under 1% of a berth frame.

What the measurements showed, recorded because the two ambient terms are not interchangeable and the next person will otherwise assume they are:

- `background_energy_multiplier` scales the **hemispheric** half of the sky ambient. It moves open decks and hull undersides and barely touches the enclosed operations room and habitat. Raising it alone flattens the frame — at 1.6 the measured per-frame standard deviation *fell*, and the backdrop stopped reading as vacuum.
- `ambient_light_energy` scales the **flat colour** quarter. It moves enclosed interiors and barely touches open decks. It is uniform by construction and is the flattening term.
- Neither substitutes for a light. The fixes that produced the largest gains were a warm shadowless bounce aimed upward (nothing previously lit any downward-facing surface in the station), and two measured facts about reach: a 39° mast cone from y = 9.0 stopped 0.7 m short of the Arrow berth it exists to light, and the freight berth's two apron work lights left a four-metre unlit seam down the exact centreline where a freighter parks.

Structural contrast — the standard deviation of the non-emissive 90% of each frame, which is what "does form read" actually means — rose in every measured frame (+4% to +44%) while the fraction of near-blown pixels moved by under 2.1 points. That is the discriminator between a lighting scheme and a gain knob, and it is the number to reproduce before accepting any future change here.

Remaining, in order of leverage:

- **Interiors are monochrome.** The operations room and habitat common room now read as manufactured plate, but every surface in them is one cyan hue. A single-hue frame is a strong "not real" cue independent of level. The exteriors got hue separation from the warm bounce; the interiors cannot see it, and their own fixtures are all cool.
- **The frame is still bimodal.** Emissive fixtures sit near 250/255 with heavy bloom while structure sits at 20–40. Real luminaires would spill onto what they are mounted to. Glow was measured and retuned by an earlier pass, so it is deliberately untouched here.
- **Two backdrop artifacts got brighter along with the ambient, and both come from values `space_backdrop_test` freezes deliberately.** They are not new; the raised hemispheric term made them about 45% more legible.
  - The procedural sky's equator is a **hard step of 8.8/255** (measured across `07_original_identity_backdrop.png`: 19.4 above, 10.6 below, over roughly ten pixels), because `sky_horizon_color` `0d1a24` and `ground_horizon_color` `070d13` are a two-to-one luminance pair with no blend between them. `sky_curve`/`ground_curve` were softened here, which smooths each hemisphere but cannot cross the equator. It reads as a ruled line, and in wide shots as a distant wall. The fix is to bring the two horizon colours together, which is a frozen identity decision.
  - The **legacy nebula cover is faintly legible as panel seams** in the same shots, roughly 4/255 of modulation over a 15/255 field. Its 0.08 modulate is frozen for the same reason.
- Frame cost of the three added lights and one added shadow map is **unmeasured**. This machine renders through llvmpipe; any number produced here would be meaningless.

**Screen-space AO cannot be evaluated on this machine.** Rendering the production scene to the root viewport under llvmpipe/Vulkan and capturing six framings, `ssao_enabled = false` at the profile level (applied before the world builds), the shipped `HIGH` settings, and a forced 4× maximum (intensity 16, radius 8 m, power 4, `light_affect` 1.0) all produce **bit-identical** frames to four decimal places on every statistic. A desaturation applied through the same Environment reference *does* land, so the reference is live and the pass is simply not contributing. Any earlier conclusion about how much AO does or does not do — including "AO's job is modulating ambient and there is almost no ambient to modulate" — was measured through an instrument that is inert on this box and needs re-taking on real hardware. The lighting result recorded above does not depend on AO either way.

## Phase 2 — Vertical slice

### Design and implementation specification

- `GameFlow` coordinates the solo loop and UI phase; it must not become the physics owner of the Player, a ship, a berth, a weapon hit, or a station door. `PlayerController` owns embodied movement, `HeroShip`/ship subclasses own craft simulation, `ShipBerth` owns lease/occupancy, `ShipBoardingArea` owns access/reservation, `CombatResolver` owns accepted hit results, and presentation components consume signals without changing those results.
- Keep the playable route physical. Core acceptance uses the production `CharacterBody3D`, real collision layers, real `InputMap` actions, real boarding areas, real seat anchors, real ship commands, and real berth leases. Teleports and direct state changes may set up a test but cannot be the evidence that the route itself works.
- Keep visible and physical geometry intentionally paired. A collision-only ramp may smooth movement only when a rendered surface occupies the same plane within the player-foot tolerance; decorative tread, inset, trim, grille, or shell meshes must be explicitly tagged non-walkable. Discover broad upward-facing route meshes in addition to maintaining a curated critical-surface roster.
- Keep movement authority and model orientation separate. Camera-relative input determines desired velocity; `CharacterBody3D` moves in that direction; the active visual mount applies only the model-specific forward-axis correction. Never fix a backwards-facing model by reversing input, velocity, camera axes, or animation semantics.
- Split material families by use. Authored ship atlases remain on their registered craft; procedural station architecture uses station-specific, lighting-neutral, tileable PBR maps with module/world-stable projection; authored hero surfaces use metric UV0. Tests must pin texture identity, importer normal convention, handedness, edge continuity, texel density, and the live material bindings rather than only checking that a texture exists.
- Landing assist is acquisition and guidance, not authority bypass. A broad capture volume may brake, stage, and align a compatible ship at forgiving speed/attitude limits; the final dock still requires the strict hull envelope, unobstructed path, valid requester-bound lease, exact berth identity, and occupy-before-snap ordering.
- Boarding reach must be wide enough for collision-clear approaches and must select the nearest eligible ship deterministically. It may not enlarge station-door reach, cross an opposite hull, ignore a disabled/reserved `ShipBoardingArea`, or clear the post-exit reboard latch before leaving the full boarding envelope.
- Combat chronology is authority first, presentation at travel arrival: health/collision/scoring resolve once; pulse receipt completion releases impact/explosion/audio once; abort/recycle releases any deferred record atomically. Pools and re-entry cleanup are bounded and cannot allocate gameplay authority.
- Vertical-slice exit gate: the complete playable-prototype gate above, plus human tuning of on-foot camera, flight, landing, boarding, combat readability, audibility, and recovery in the same packaged candidate.

4. **Boarding:** reserve the area, generation-guard the asynchronous transition, disable embodied collision only after the transition owns the live seat, parent/follow the seat through the existing Player API, and release reservation/state on cancellation, destruction, detach, or reuse.
5. **Startup/launch:** send engine requests through `GameFlow`/the ship's public method, clear parked input, wait for `ENGINE_ONLINE`, bind the active camera and command source once, then accept sustained departure input. A tap must not clear landed authority.
6. **Flight/fire:** populate one `ShipCommand` snapshot per physics tick, validate the source, and let the ship consume that snapshot. Fire through combat authority/resolver; never apply damage from the pulse mesh or audio callback.

8. **Shutdown/exit:** require landed + occupied + engine offline, run generation-guarded disembark, restore the production capsule at `get_exit_transform()`, clear the seat/active-ship/camera exactly once, and update guided completion only after the physical exit signal.
9. **Recovery/reuse:** on destruction, clear pending landing/boarding/receipts, restore on-foot authority, regenerate only when the home berth can be reserved, and preserve object/connection counts across whole-`Main` detach/re-entry.

**Required tests for any loop change:** start with the affected component test, then add/extend `station_surface_playability_test.gd`, `boarding_accessibility_test.gd`, `controller_physical_sortie_test.gd`, `controller_sortie_lifecycle_test.gd`, `torrent_sortie_completion_test.gd`, `sandbox_loop_test.gd`, `fleet_lifecycle_safety_test.gd`, `main_reentry_quality_test.gd`, and `smoke_test.gd` as applicable. ## Phase 3 — Shipyard expansion (bounded operational-lattice slice settled; full phase incomplete)

### Design and implementation specification

- Build each station addition as a bounded module scene with a stable module ID, identity connection anchor, local footprint/AABB, route-marker registry, evidence metadata, semantic component roster, collision/authority/performance report, validation API, and reversible enable/disable lifecycle. World integration owns the global transform and any shared gameplay authority.
- Preserve a single station graph. A module publishes connection planes and route endpoints; `ShipyardWorld` chooses placement and proves adjacency. Do not hide disconnected geometry with teleport triggers, duplicate floors, invisible bridges, or presentation-only shells that imply a route the player cannot walk.
- Separate walkable structure from dressing. Walkable decks, ramps, stairs, shelves, and thresholds use World-layer static collision matched to their visible envelope. Pipes, labels, rails, lamps, trim, machinery covers, and distant shells are collision-free unless they intentionally block the player, and non-walkable horizontal presentation is tagged for discovery audits.
- Keep berth, regeneration, door, activity, and audio ownership external or explicit. A decorative dock marker cannot reserve a ship; a labelled control cannot regenerate one; an activity rail cannot become navigation; an ambience emitter cannot drive a door. New modules consume the existing component APIs instead of creating lookalike local authority.
- Integrate in dependency order: evidence/topology claim → isolated module scene → module audit/test → collision-clear connection transform → production-world route test → nearby berth/ship-envelope regression → Main detach/re-entry → native overview and player-height review.
- Expansion acceptance requires: no changed existing berth transforms/leases unless explicitly scoped; continuous no-jump route from an existing hub; published negative-space samples remain empty; visible floor support discovery stays green; no overlap with landing capture/final hull envelopes; quality-profile budgets are bounded; full core-loop/package gates remain green.
